# Log Agent 项目介绍口述稿

> 面向岗位：校招 Agent 开发
> 使用原则：按面试时间选择一档直接朗读，不要把四档连续念完。
> 事实口径：飞书功能已实现，真实平台验收待权限；真实 SLS 与真实方舟已通过本地 Web 联合链路验证。

## 1. 一句话版本

我用 Go 和 Eino 做了一个受治理的日志排障 Agent，
它能从飞书或本地网页接收请求，安全查询阿里云 SLS，
把当前窗口与基线窗口整理成可追溯证据，
再由规则和火山方舟生成可读报告。

## 2. 三十秒版本

面试官您好，
我做的是一个 Go 日志排障 Agent。

它解决的问题是，
传统排障需要工程师手动确认权限、拼查询、对比时间窗口，
最后还要把零散结果整理成结论，整个过程比较慢，也很难复盘。

我的方案不是让大模型自由翻日志，
而是用 Eino 编排一条固定调查图，
所有真实 SLS 查询都先经过权限、模板、时间窗、并发和审计检查，
查询结果再形成带编号的 Evidence。

规则引擎先做确定性判断，
火山方舟只基于这些证据生成摘要，失败时会自动回退，
不会影响主调查结果。

目前飞书接收、卡片动作和可靠投递功能已经实现，
真实 SLS 与真实方舟也通过本地 Web 联合跑通；
飞书真实平台验收还在等待应用权限。

## 3. 三分钟版本

面试官您好，
我想介绍一个我重点准备的项目：日志排障 Agent。

这个项目最开始想解决一个很具体的问题。
当同事说“某个环境的错误是不是突然变多了”，
有经验的工程师不会马上搜几条日志就下结论。
他会先确认谁在查、查哪个服务、时间范围多大，
然后把当前窗口和前一个基线窗口放在一起比较，
最后说明数据是否完整、结论依据是什么。

我希望把这套排查思路做成一个 Agent，
但又不能让它像普通聊天机器人一样自由发挥。
因为日志查询涉及权限、成本和敏感信息，
一次错误的工具调用比一句错误的回答危险得多。

所以我把它设计成一名“拿着授权清单办案的值班工程师”。
用户可以从飞书或本地网页发起调查，
入口只接收服务、环境和时间窗口，
不允许用户直接指定物理日志库、查询语句或身份。

请求进来后，
系统先在 SQLite 里做幂等接单，
给这次调查生成一个像快递单号一样的 Investigation ID。
即使平台重复投递同一条消息，
系统也只创建一份调查，不会重复查询云日志。

接下来 Worker 用租约领取任务，
Eino 按固定顺序执行调查：
先规划当前窗口和基线窗口，
再查询、生成 Evidence、构建报告，
最后按条件补充变更或运维信号。

我没有采用完全开放的 ReAct，
因为模型自由选择工具虽然灵活，
但查询次数、权限范围和故障恢复都很难控制。
固定 Graph 让每一步都能测试、审计和回放，
也能估算一次调查最多发起多少外部调用。

真正访问阿里云之前，
每个请求都必须通过 Query Gateway。
它像数据中心门禁一样，
校验可信身份、逻辑资源、ACL、固定模板、时间窗口、
日志摄入水位、索引 Schema、并发和预算。
只有这些条件都满足，
才会通过本机阿里云 CLI 和 STS 临时凭据发起只读 SLS 查询。

查询回来以后，
我不会只保存一句“错误增加了”。
系统会形成一份证据卷宗，
记录查了哪个逻辑范围、什么时间、用了哪个模板，
结果是否完整、是否截断，以及对应的 Evidence ID。
报告里的结论必须引用这些 ID，
这样面试官或值班人员可以继续追问“这句话依据在哪”。

LLM 放在事实层之后。
规则引擎先比较当前和基线，生成确定性结论，
火山方舟只拿到脱敏后的聚合证据，
看不到原始日志、凭据、用户身份和物理 Logstore。
模型输出还要经过证据引用和建议范围校验。
如果超时、额度不足或输出不合规，
系统保留原来的规则报告并使用回退摘要，
不会把整个调查判失败。

可靠性方面，
我把调查、查询步骤和结果投递分别持久化。
如果当前窗口已经查完但进程崩溃，
重启后可以复用满足相同治理指纹的 Checkpoint；
如果外部请求到底有没有成功无法判断，
系统不会盲目重试，而是进入人工复核。
投递失败也只重试投递，
不会为了补发一张卡片重新查日志和调用模型。

目前项目的飞书接收事件、卡片动作、回复更新和可靠投递功能已经实现。
由于真实应用权限还没获批，
我增加了只监听本机地址的 Web 控制台，
用同一套 Intake、Worker、Eino、SQLite 和 Delivery 合同完成操作闭环。

在这个入口上，
我已经把真实阿里云 SLS 和真实火山方舟串进同一次调查。
一次记录中的当前窗口和基线窗口都完整返回，
模型摘要也成功生成并记录了 Token 和延迟。
这些数字只代表那一次本地联合样本，
我不会把它说成生产 SLA。

我认为这个项目最有价值的地方，
不是简单接了两个 API，
而是把 Agent 的自主性、真实工具权限、故障恢复、证据约束和离线评测连成了一条工程链。

当前边界也很清楚：
真实试点先使用单个主 Logstore 的 count-only 模板，
SQLite 还是单实例技术预览，
跨八个日志库、真实 Metrics 和 Trace、企业 Runbook、
以及飞书平台环境验收都属于下一阶段。

## 4. 五分钟版本

面试官您好，
我介绍一下我的日志排障 Agent 项目。

我做这个项目，不是因为想再做一个“能聊天的机器人”，
而是观察到日志排障里有大量重复但又不能草率自动化的工作。

比如有人问：
“测试环境这个服务最近十分钟错误是不是变多了？”

工程师通常要先找到正确日志库，
确认环境字段和错误级别字段，
再查当前窗口、找一个可比较的基线，
还要判断日志是否延迟到达、查询有没有截断。
最后，他需要把这些证据整理成别人能看懂、能复核的结论。

如果只是写几个固定脚本，
后续很难扩展不同调查模板和交互入口；
如果完全交给大模型自由调用工具，
又会面临越权查询、成本失控、提示注入和结论幻觉。

所以我采用了一个中间方案：
把它做成“受治理的固定图 Agent”。

可以把整个系统想成一个办案流程。
飞书或本地 Web 是报案大厅，
Intake 是登记员，
SQLite 是案卷室，
Worker 是领案的调查员，
Eino 是标准办案流程，
Query Gateway 是权限门禁，
Evidence 是带编号的证物，
LLM 则是负责把卷宗写成通俗摘要的文书。

第一步是接单。
入口只允许用户表达业务范围，
也就是服务、环境、时间窗口和允许的调查模板。
身份从服务端或飞书事件信封中获取，
不会相信用户在文本里写的身份。

Intake 会用应用、租户和消息 ID 做幂等接单。
这相当于快递系统的运单号：
网络重试可以重复提交，但仓库里只有一份真实任务。
这样既保护云查询费用，
也避免用户收到两份互相冲突的报告。

第二步是可靠执行。
Worker 不是从内存队列拿任务，
而是从 SQLite 领取一份带期限的租约。
运行过程中持续续租，
旧 Worker 丢失租约后不能再写终态。
如果进程退出，
租约过期后新 Worker 可以接管。

第三步是 Agent 编排。
我使用 Eino Graph，
但只让它负责编排，不让它成为状态真相。
Graph 按固定顺序规划当前和基线查询、执行查询、构建报告，
再根据已有证据决定是否补充关联信号。

这样做的原因是，
日志 Agent 的高风险点不是“回答不够有创意”，
而是“工具调用不可控”。
固定图牺牲了一部分自由探索能力，
换来了调用上界、稳定回放、节点级测试和清晰故障定位。

第四步是查询治理。
Eino 不能直接访问阿里云。
每个 QuerySpec 都必须进入 Query Gateway，
依次通过身份、ACL、Catalog、模板、Schema、时间窗、
摄入水位、并发、额度和审计检查。

这里一个关键设计是，
用户只能说“查哪个逻辑服务和环境”，
不能传 Project、Logstore 和查询语句。
物理资源由管理员 Catalog 解析。
这样新增 Web 或飞书入口时，
不会因为入口实现不同而绕过权限。

真实 SLS 接入最终没有继续走 SDK，
而是复用了公司现有的阿里云 CLI + STS Profile。
用户通过 SSO 获取临时凭据并配置到本机，
CLI 负责读取 Profile、签名和发起 HTTPS 请求，
Agent 不读取凭据文件，也不长期保存 AK、SK 或 Token。

当然，CLI 也有自己的风险。
所以我的 Go 适配器不用 Shell 拼字符串，
只允许固定子命令和安全参数，
限制输出大小和超时，清理可能覆盖凭据的环境变量，
也不会把云端错误 Body 和查询内容直接回显。

第五步是证据建模。
Provider 返回的计数不会直接变成一句自然语言。
系统先保存 QuerySpec 哈希、模板版本、治理指纹、
完整性、截断、水位和用量信息，
再生成稳定 Evidence ID。

当前窗口和基线窗口都完整，
系统才允许做确定性比较；
如果数据不完整，就明确降级，
而不是为了给用户一个答案强行判断。
每条 Finding 都要引用 Evidence ID，
这让报告可以审计、回放，也便于构造反证测试。

第六步才是 LLM 摘要。
我把火山方舟放在规则报告之后，
它收到的是最小化、脱敏后的 Evidence，
不是原始日志。
请求关闭服务端存储并限制输出 Token，
响应要求符合严格结构。

模型返回后，
应用还要检查它引用的证据是否存在、
建议是否来自已批准列表、
有没有编造 count-only 数据里不存在的错误类型或根因。
任何检查失败都会丢弃模型草稿并回退。

第七步是恢复和投递。
当前窗口与基线窗口分别有持久化 Checkpoint。
复用时不仅比较请求参数，
还比较 Catalog、策略、模板和 Schema 形成的治理指纹。
只要治理发生变化，旧结果就不能直接复用。

对于“请求可能已经到达 Provider，但本地没有收到结果”的情况，
我没有粗暴地自动重试，
而是把状态标记为需要人工复核。
这是因为网络超时不等于远端没执行，
盲目重试可能重复花费。

报告保存后，Delivery Worker 再独立投递。
飞书暂时失败时，
系统只重试卡片投递并管理死信，
不会重新跑 SLS 和 LLM。

在验证方面，
我不只测正常成功路径。
测试覆盖重复消息、租约接管、旧 Worker 迟到写入、
未授权查询、超出时间窗、日志尚未过水位、
治理漂移、外部结果未知、模型编造证据、
Token 配额和投递死信。

项目还提供 Golden Dataset、Snapshot 和 Replay Compare，
用于比较规则或 Prompt 变化前后的行为。
如果两个版本的输入合同不可比，
系统会明确拒绝输出伪精确的差异。

现在的完成度是：
Go Agent 主链、飞书功能、本地 Web、SLS CLI 适配器、
火山方舟摘要、SQLite 恢复和离线评测都已经实现。
真实阿里云 SLS 与真实火山方舟已经在本地 Web 的同一次调查中串联成功。

我会明确说明两个验收边界。
第一，飞书功能代码已经完成，
但真实应用权限尚未拿到，所以平台事件和真实卡片还待验收。
第二，真实 DAM 试点当前只使用单主 Logstore 的 count-only 模板，
不能把它描述成八库统一根因分析。

如果继续推进，
我会先完成真实飞书平台验收，
再引入脱敏专家反馈扩充评测集，
最后根据实际需求决定是否做多 Logstore、真实 Metrics/Trace 和高可用存储。

这个项目让我最深的体会是：
Agent 开发的难点不是把模型接上，
而是把模型和真实工具放进一个即使失败也能解释、能恢复、能审计的系统里。

## 5. 口述时的取舍提示

如果面试官偏 Agent，
重点讲固定 Graph、Query Gateway、Evidence-only LLM 和评测。

如果面试官偏 Go 后端，
重点讲幂等接单、租约、Attempt Fence、Checkpoint、Delivery 和 SQLite 事务。

如果面试官追问真实效果，
先说明真实 SLS + 真实方舟的联合链路已跑通，
再主动补充它是单 Logstore、count-only、本地样本，
不要把一次样本包装成生产指标。

如果面试官追问飞书，
可以直接说接收事件、卡片动作、Reply/Patch 和可靠投递已经实现，
当前只差企业应用权限下的真实平台验收。

> 💡 **一句话记住**：先讲它像一名“有授权、按流程、留证据”的值班工程师，再用固定图、治理门禁、证据摘要和故障恢复证明它不是普通聊天机器人。
