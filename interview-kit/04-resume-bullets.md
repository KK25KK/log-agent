# Log Agent 校招简历条目候选

> 目标岗位：Agent 开发 / Go 后端
> 使用建议：最终只选 2～3 条，不要把七条全部塞进一份简历。
> 真实性原则：只选择你能现场解释设计、演示项目并回答取舍的内容；不要写“独立上线”“生产准确率”等未验证表述。

## 1. 怎么选，而不是怎么堆

校招简历的一条项目描述，
最好同时回答两个问题：

1. 你具体解决了什么问题；
2. 你的设计带来了什么可验证效果。

技术名只是证据，不是主角。
“使用 Go、Eino、SQLite、SLS、LLM”像在报菜名；
“用固定图和治理网关限制真实日志工具调用”才是在讲工程能力。

下面七条都尽量控制在三十个中文字符左右。
字符统计按可见字符近似，英文缩写、数字和标点都按一个字符看待；
不同招聘系统的计数规则可能略有差异，粘贴后应再检查一次。

## 2. 候选一：Agent 固定图编排

### 简历短句

> 基于Go/Eino实现可审计日志排障Agent

推荐等级：★★★★★；适合强调 Agent 架构、工具调用约束和框架边界。

### 业务背景

传统日志排障依赖工程师手动选择时间窗口、查询日志和整理结论。
开放式 Agent 可能自由扩大查询范围、重复调用工具，难以控制权限、费用和结果复现。

### 具体做了什么

设计并实现固定调查图，把一次调查拆成规划当前/基线查询、执行查询、构建报告、关联信号四个节点。
应用层通过统一 Engine 端口调用，Eino 只存在于适配层。

证据入口：
[engine.go](file:///D:/日志agent/internal/adapters/eino/engine.go#L90-L182)
和 [ports.go](file:///D:/日志agent/internal/ports/ports.go#L75-L89)。

### 为什么这么实现

固定图牺牲部分自由探索能力，换来确定的节点顺序、调用上界、失败定位和离线回放。
Eino 与应用端口隔离后，未来替换编排框架不需要重写状态机和治理逻辑。

### 为什么不选别的方案

没有选择完全自研编排，
因为 Eino 已提供图组合、编译与回调能力，可以减少样板代码。
也没有选择开放式 ReAct，
因为当前工具是有权限和费用风险的真实日志查询。

### 可验证效果

固定节点的成功、失败与跳过状态都有自动化测试；
Mock 全链测试覆盖从请求进入到报告投递的合同；
真实 SLS 与真实方舟已在同一次本地 Web 调查中串联成功。

这里的“效果”是链路和行为边界可验证，
不是生产准确率或大规模吞吐指标。

### 技术水平说明

这条体现的是中等偏上的校招 Agent 工程能力：
不仅会调用框架，还能决定框架应该负责什么、不应该负责什么。

### 适用前提

你要能画出固定 Graph，
解释为什么 Eino 不保存状态，
并讲清固定图与开放式 Agent 的取舍。

### 可以说 / 不能说

可以说：实现了受治理的固定图日志 Agent，并完成真实工具联合链路验证。

不能说：实现了能自主处理所有日志故障的通用 Agent。

## 3. 候选二：查询治理网关

### 简历短句

> 构建SLS查询治理网关，默认拒绝越权调用

推荐等级：★★★★★；适合强调安全工程、云工具治理和后端设计。

### 业务背景

日志 Agent 连接真实 SLS 后，用户能使用 Agent 不代表能访问任意 Project、Logstore 或时间范围。
权限、成本、数据完整性和审计必须在调用前统一判断。

### 具体做了什么

建立单一 Query Gateway，依次完成可信身份、Catalog、ACL、固定模板、Schema、
时间窗、水位线、并发、预算与审计检查，
只有通过后才调用 Provider。

证据入口：
[gateway.go](file:///D:/日志agent/internal/application/query/gateway.go#L95-L225)
和 [gateway_test.go](file:///D:/日志agent/internal/application/query/gateway_test.go#L230-L302)。

### 为什么这么实现

所有入口共享一个窄门，
可以避免 Web、飞书或未来 API 各自复制权限逻辑。
用户只表达逻辑服务和环境，物理资源由管理员 Catalog 解析，
避免请求参数直接变成云资源访问能力。

### 为什么不选别的方案

没有把 ACL 写进 SLS Adapter，
因为 Adapter 只应处理 Provider 协议，不应决定业务权限。
也没有查询后再补审计，
因为审计失败时真实访问已经不可撤回。

### 可验证效果

自动化测试证明未授权、超窗、水位未过、Schema 错误和审计失败
都会在 Provider 读取前失败关闭；
并发与超时也有独立测试。

### 技术水平说明

这条体现从“能调 API”走到“能治理 API”的能力，
适合安全敏感的 Agent 或平台后端岗位。

### 适用前提

你要能按顺序讲出治理链，
解释逻辑资源与物理资源为什么分离，
并举出一个查询前必须失败的例子。

### 可以说 / 不能说

可以说：代码默认拒绝未授权和不满足预算的数据访问。

不能说：代码已经代替管理员完成所有云端 RAM 权限治理。

## 4. 候选三：任务恢复与费用保护

### 简历短句

> 设计租约与Checkpoint，支持任务故障恢复

推荐等级：★★★★★；适合强调 Go 并发、状态机、可靠性和外部调用语义。

### 业务背景

当前窗口查完后进程可能崩溃，如果重启后全部重做会重复花费；
但请求超时时直接重试，也可能重复执行已经到达云端的查询。

### 具体做了什么

组合 Job Lease、Attempt Fence 和 QueryStep Checkpoint：
Worker 用租约领取并续租任务；
current 与 baseline 独立记录状态；
已成功步骤在治理指纹一致时跨重启复用；
外部结果未知时进入人工复核。

证据入口：
[checkpoint_executor.go](file:///D:/日志agent/internal/application/checkpoint_executor.go#L23-L137)
和 [worker.go](file:///D:/日志agent/internal/application/worker.go#L70-L175)。

### 为什么这么实现

数据库事务无法包住远程请求，因此项目不虚构 Exactly Once，
而是用持久化步骤、fencing 和显式未知状态限制重复风险。

### 为什么不选别的方案

没有采用“任何错误重试三次”，
因为网络超时只表示客户端不知道结果。
没有只使用内存状态，
因为进程退出后无法恢复已经完成的查询窗口。

### 可验证效果

测试覆盖租约过期接管、旧 Worker 迟到写入拒绝、
Checkpoint 跨进程复用、治理漂移拒绝和 UNKNOWN 转人工复核。

效果是故障恢复行为可预测，
不能表述为真实生产环境已经达到 Exactly Once。

### 技术水平说明

这条比“用了 SQLite”含金量高，
因为它展示了对分布式外部调用不确定性的理解。

### 适用前提

你要能解释 Lease、Attempt、Checkpoint 各自解决什么问题，
也要承认当前 SQLite 是单实例技术预览。

### 可以说 / 不能说

可以说：实现了崩溃恢复与重复调用保护，并对未知结果失败关闭。

不能说：实现了跨云服务的严格 Exactly Once。

## 5. 候选四：Evidence 约束 LLM

### 简历短句

> 建立Evidence约束，拦截LLM无依据摘要

推荐等级：★★★★★；适合强调 LLM 安全、结构化输出和幻觉治理。

### 业务背景

LLM 能提升报告可读性，但原始日志可能包含敏感信息和提示注入，
模型也可能引用不存在的证据或猜测 count-only 数据里没有的根因。

### 具体做了什么

先由规则层生成 Evidence、Finding 和 Recommendation，再构造不含原始日志、身份、查询和物理资源的最小摘要输入。
方舟返回严格结构后，应用校验证据 ID、建议代码和内容安全，
失败则回退到确定性摘要。

证据入口：
[summary.go](file:///D:/日志agent/internal/application/summary.go#L29-L205)
和 [summarizer.go](file:///D:/日志agent/internal/adapters/volcark/summarizer.go#L131-L228)。

### 为什么这么实现

事实判断与语言生成分开后，
模型变成“有卷宗的文书”，而不是“自由办案的人”。
即使模型不可用，主调查仍能成功。

### 为什么不选别的方案

没有只靠 Prompt 写“不要编造”，
因为软约束无法替代输出校验。
没有直接传原始日志，
因为它会扩大数据泄露面和 Token 成本。

### 可验证效果

自动化测试覆盖 grounded 输出、虚构证据、敏感输入、
count-only 越界推断、额度拒绝和 Provider 失败回退。
真实方舟也在联合调查中成功生成过 MODEL 摘要。

一次样本的 Token 和延迟只能作为验收记录，
不能写成稳定性能指标。

### 技术水平说明

这条体现的不只是 Prompt Engineering，
而是 LLM 输入最小化、结构化输出、应用层验证和可降级设计。

### 适用前提

你要能解释 Evidence 为什么先于 LLM，
并现场举例说明模型输出在哪些情况下会被丢弃。

### 可以说 / 不能说

可以说：真实方舟已接入，且模型输出受 Evidence 与额度双重约束。

不能说：LLM 已经能够准确判断真实根因。

## 6. 候选五：真实 SLS 的 CLI + STS 接入

### 简历短句

> 通过CLI+STS接入真实SLS，避免持久凭据

推荐等级：★★★★☆；适合强调真实系统接入、安全边界和适配器设计。

### 业务背景

企业已有 SSO 发放 STS、本机 CLI 管理 Profile 的认证路径。
如果 Agent 单独持有长期 AK/SK，会增加凭据分发、保存与轮换成本。

### 具体做了什么

将真实 SLS 路径从 SDK 调整为受控 CLI Adapter，复用本机 StsToken Profile 完成签名。
Adapter 固定子命令和参数，校验资源字符，限制超时和输出，
清理凭据覆盖环境变量并脱敏错误。

证据入口：
[backend.go](file:///D:/日志agent/internal/adapters/aliyuncli/backend.go#L33-L170)
和 [backend_test.go](file:///D:/日志agent/internal/adapters/aliyuncli/backend_test.go#L212-L317)。

### 为什么这么实现

这样可以复用组织现有认证流程，
Agent 不需要读取 Profile 文件，也不长期保存云凭据。

### 为什么不选别的方案

SDK 的类型安全和性能更好，
但当前阶段需要另建凭据注入与轮换链路。
CLI 更适合快速完成只读试点，
前提是绝不通过 Shell 拼接用户输入。

### 可验证效果

8 个 Logstore 的 CLI 访问曾人工检查通过；
Agent 在单主 Logstore 上完成真实 count-only 联合调查。

这证明真实连接和单库模板工作，
不代表 Agent 已实现 StoreView 自动展开或八库统一时间线。

### 技术水平说明

这条展示根据企业认证现实调整技术方案的能力，
也能体现对进程执行和凭据面的安全意识。

### 适用前提

你要能解释 CLI 为什么没有直接接触聊天文本，
以及 STS 过期、CLI 缺失、插件错误分别如何诊断。

### 可以说 / 不能说

可以说：真实 SLS 已通过 CLI + STS 接入并完成单库联合验证。

不能说：已经覆盖所有 Logstore 或完成生产凭据托管。

## 7. 候选六：可靠投递与死信

### 简历短句

> 实现可靠投递与死信重放，隔离调查失败

推荐等级：★★★★☆；适合强调消息可靠性、最终一致性和飞书工程接入。

### 业务背景

调查成功后，飞书短暂不可用不应该让报告丢失，
更不应该为了补发卡片重新查询 SLS 和调用 LLM。

### 具体做了什么

将报告落库与投递拆开，DeliveryWorker 使用独立租约、发送超时、失败分类、指数退避和死信；
卡片初始 Reply、进度 Patch 与终态 Patch 保持顺序，
允许 Operator 安全重放符合条件的死信。

证据入口：
[delivery.go](file:///D:/日志agent/internal/application/delivery.go#L13-L94)
和 [delivery_test.go](file:///D:/日志agent/internal/adapters/sqlite/delivery_test.go#L13-L124)。

### 为什么这么实现

调查和投递是两类不同的外部失败。
分开持久化后，报告先成为事实，
消息平台恢复后再完成最终一致投递。

### 为什么不选别的方案

没有在用户请求中同步等待整条调查和卡片发送，
因为任何一段超时都会诱发上游重复提交。
也没有无限重试，
因为永久错误需要进入死信并由人处理。

### 可验证效果

飞书接收、动作、Reply/Patch 和可靠投递代码已经实现；
测试覆盖顺序、重试、死信与旧进度不能覆盖新终态。
真实平台验收仍需飞书应用权限。

### 技术水平说明

这条体现 Outbox 风格的可靠投递思路，
比“接入飞书机器人”更能展示后端工程深度。

### 适用前提

你要能解释调查成功与投递成功为什么是两个状态，
并说明哪些错误可以重试、哪些应该进死信。

### 可以说 / 不能说

可以说：飞书交互和可靠投递功能已完成，平台验收待权限。

不能说：真实飞书链路已经上线运行。

## 8. 候选七：Agent 离线评测与回放

### 简历短句

> 搭建Golden与Replay评测，防止Agent退化

推荐等级：★★★★☆；适合强调 Agent 评测、版本治理和质量工程。

### 业务背景

调整规则、阈值或 Prompt 后，几个顺眼的成功案例不能证明 Agent 没有退化。
真实日志又会随时间变化，直接重跑两个版本不公平。

### 具体做了什么

建立固定 Golden Dataset、版本指纹、评测快照和 Replay Compare；门禁同时检查成功输出、证据引用、误导结论和反证场景；
两个快照合同不兼容时明确标记不可比较。

证据入口：
[evaluate.go](file:///D:/日志agent/cmd/logagent/evaluate.go#L82-L223)
和 [evaluate_test.go](file:///D:/日志agent/cmd/logagent/evaluate_test.go#L14-L224)。

### 为什么这么实现

先保存稳定输入与输出快照，
才能在不重复访问真实外部系统的情况下比较两个版本。
反证门禁可以检查 Agent 什么时候应该拒绝结论。

### 为什么不选别的方案

没有只依赖单元测试，
因为局部函数正确不等于最终报告忠实。
也没有直接做线上 A/B，
因为当前缺少真实流量隔离和专家标签，成本过高。

### 可验证效果

测试覆盖固定 Golden、误导性 Finding 失败关闭、
快照 lineage、严格回放和不可比较边界。

它能证明定义过的安全场景没有回归，
不能推出真实根因准确率。

### 技术水平说明

这条展示了把 Agent 当成可持续迭代的软件系统，
而不是一次性 Demo。

### 适用前提

你要能解释 Golden、Snapshot、Replay 各自解决什么问题，
也要承认当前数据以合成和离线场景为主。

### 可以说 / 不能说

可以说：建立了可回放的离线安全门禁，能发现已定义场景的退化。

不能说：离线评测已经证明线上准确率。

## 9. 三套最终组合建议

### 组合 A：Agent 主线版（首选）

适合投递 Agent 开发、大模型应用工程岗位。

建议选择：

1. 基于Go/Eino实现可审计日志排障Agent；
2. 构建SLS查询治理网关，默认拒绝越权调用；
3. 建立Evidence约束，拦截LLM无依据摘要。

这组三条形成完整故事：
如何编排 Agent、如何管住真实工具、如何管住模型输出。

### 组合 B：Go 工程版

适合投递 Go 后端、平台工程、基础架构岗位。

建议选择：

1. 设计租约与Checkpoint，支持任务故障恢复；
2. 实现可靠投递与死信重放，隔离调查失败；
3. 构建SLS查询治理网关，默认拒绝越权调用。

这组三条突出状态机、并发控制、失败恢复和安全门禁。

### 组合 C：Agent 可靠性版

适合强调 LLMOps、Agent 质量和安全方向。

建议选择：

1. 建立Evidence约束，拦截LLM无依据摘要；
2. 搭建Golden与Replay评测，防止Agent退化；
3. 设计租约与Checkpoint，支持任务故障恢复。

这组三条回答“模型说错怎么办、版本退化怎么办、执行中断怎么办”。

## 10. 最终推荐

如果简历只能放两条，优先使用候选一和候选四：

- 第一条说明你做了一个怎样的 Agent；
- 第二条说明你不是简单接模型，而是解决了 Evidence 与幻觉问题。

如果能放三条，再按岗位选择：

- 偏 Agent：补候选二；
- 偏 Go：补候选三；
- 偏平台接入：补候选五；
- 偏质量工程：补候选七。

无论选择哪一组，
都不要同时写“真实联合验证”和“生产上线”。
当前可信表述是：
飞书功能已实现，真实平台验收待权限；
真实 SLS + 真实方舟已通过单 Logstore、count-only 的本地联合调查。

> 💡 **一句话记住**：简历只放最能证明你判断力的两三条，让每条都能从业务问题讲到方案取舍、测试证据和现实边界。
