# Log Agent 简历条目逐条面试脚本

> 面向岗位：校招 Agent 开发
> 对应关系：本文件的 1～7 与《04-resume-bullets.md》的候选 1～7 完全一致。
> 使用方法：先背每条的 20～30 秒开场，再理解 2～3 分钟完整版和追问，不要机械背诵技术名。

## 0. 通用表达原则

每条回答都按同一条逻辑线展开：

问题是什么，
我为什么选择这个方案，
它怎样落地，
产生了什么可验证效果，
又牺牲了什么。

遇到真实系统问题时，
要主动区分“代码实现”“自动化测试”“真实联合验收”和“生产上线”。

本项目当前可以统一这样描述：

飞书接收、卡片动作、Reply/Patch 与可靠投递功能已经实现，
真实平台验收等待应用权限；
真实阿里云 SLS 与真实火山方舟已经通过本地 Web 串进同一次调查；
真实试点是单主 Logstore、count-only 模板，
不是八库统一根因分析，也不是生产 SLA 证明。

## 1. 基于Go/Eino实现可审计日志排障Agent

### 20～30 秒开场

我用 Go 和 Eino 做了一个受治理的日志排障 Agent。
它不会让模型自由拼查询，
而是按固定图完成当前窗口、基线窗口、证据生成和报告构建。
所有状态、权限和 Evidence 都由应用层管理，
Eino 只负责编排。
这样既保留 Agent 调用真实工具的能力，
又能控制查询上界、审计每一步并稳定回放。

### 2～3 分钟完整口述

这条简历想表达的核心不是“我用了 Eino”，
而是我解决了 Agent 自主性和真实工具风险之间的冲突。

日志排障很适合 Agent：
它要理解一个调查目标，
规划当前和基线两个观测窗口，
调用日志工具，再根据结果生成结论。

但它又不是一个可以自由试错的聊天任务。
日志背后有权限、敏感数据和查询费用，
如果让模型使用开放式 ReAct 自己决定查什么，
同一个输入可能产生不同路径，
还可能扩大时间范围或反复调用工具。

所以我把 Agent 设计成一名按标准流程办案的值班工程师。
Eino Graph 只有四类固定节点：
规划查询、执行查询、构建报告、关联受控信号。
每个节点输入输出都是领域对象，
不是一段模型随意生成的文本。

应用层只依赖一个 InvestigationEngine 接口。
Eino 放在 Adapter 中，
不会持有任务真相，也不会直接管理权限和数据库状态。
任务状态、租约、Checkpoint、Evidence 和投递都在 Go 应用层。

这样做的第一项收益是确定性。
一次调查最多走哪些节点、调用几次 SLS，
可以在执行前估算。

第二项收益是可测试。
我能分别验证节点成功、失败和跳过，
也能验证证据不完整时不能生成确定性结论。

第三项收益是可替换。
如果以后换编排框架，
应用层的接单、治理、恢复和报告合同不需要推倒重写。

它的代价也很明确：
固定图不能临场发明全新的排障策略，
新增调查类型需要注册新模板或节点。

我认为这个取舍适合第一阶段。
先把高频、边界清楚的错误突增调查跑稳，
以后再考虑让策略层从已批准模板中做有限选择，
而不是一开始就把所有工具控制权交给模型。

目前这条主链已经有自动化测试，
并且在本地 Web 入口串联过真实 SLS 和真实方舟。
我会把它称为真实工具联合验收，
不会称为生产大规模上线。

### 追问一：固定流程还算 Agent 吗？

算。
Agent 的关键是围绕目标感知状态、规划步骤并调用工具，
不是必须拥有无限自主权。
这个项目把自主范围限制在批准的调查合同里，
更适合日志这种高风险工具场景。

### 追问二：为什么不用纯 Go 自己写状态机？

纯 Go 完全可以实现，
但 Eino 已经提供图组合、编译和节点观测能力，
能减少编排样板。
我自己掌握的是权限、状态、Evidence 和恢复这些业务核心，
框架只承担可替换的流程组织。

### 追问三：为什么不采用开放式 ReAct？

ReAct 的优势是探索能力强，
但当前日志工具有费用和权限边界。
开放式路径会让调用次数、参数和重试语义难以证明。
第一阶段我更看重可控和可复现，
后续可以只开放“从批准模板中选择”这一层自主性。

### 追问四：怎么证明 Eino 没有侵入业务层？

应用层只通过统一 Engine 接口工作，
领域对象里没有 Eino 的状态类型。
架构测试还会扫描依赖边界，
因此不是口头约定，而是可持续检查的约束。

### 边界防守

我能证明固定图、应用主链和真实工具联合样本已经完成。
我不能声称这个 Agent 能覆盖所有故障类型，
也不能声称固定图已经在生产流量下证明性能。

## 2. 构建SLS查询治理网关，默认拒绝越权调用

### 20～30 秒开场

我没有让任何入口直接调用 SLS，
而是建立一个统一 Query Gateway。
它会在读取日志前完成身份、ACL、逻辑资源、固定模板、
Schema、时间窗、水位、并发、预算和审计检查。
任何环节不满足都默认拒绝，
所以 Web、飞书和未来 API 都共享同一套数据访问边界。

### 2～3 分钟完整口述

这条解决的是“Agent 能查日志以后，怎么保证它只查该查的数据”。

普通 SLS Client 关注的是请求能不能成功。
企业内部 Agent 还要回答：
是谁在查，为什么允许，
查哪个业务服务，窗口多大，
索引能不能支持这个结论，
费用有没有超过上限，
每次访问是否留下审计。

如果这些判断散落在飞书、Web、Worker 和 SLS Adapter 里，
新增一个入口就可能漏掉一层。
所以我建立了单一 Query Gateway，
它是所有真实日志读取必须经过的窄门。

用户提交的只是逻辑服务、环境和时间窗口。
他不能直接传 Project、Logstore 或查询表达式。
Gateway 先用管理员维护的 Catalog 解析物理资源，
再用从可信入口信封得到的 Principal 做 ACL 判断。

通过身份检查后，
系统还要验证资源绑定的固定模板和索引 Schema。
例如 count-only 模板只需要环境和错误级别，
不能因为缺少错误类型字段就强行做 Top Error。

时间方面还有两道门。
第一道限制最大窗口，防止一次请求扫描过多日志；
第二道是日志摄入水位，
避免最新几分钟的日志还没到齐，就把零结果当成真实没有错误。

随后 Gateway 占用并发和预算许可，
先写 STARTED 审计，再调用 Provider。
如果开始审计写不进去，
真实日志读取不会发生。

Provider 返回后，
系统重新检查超时 Context，
避免一个已经超过应用截止时间的迟到响应被当成确定性证据。
结果还会被归一化并写终态审计。

我没有把这些规则写进阿里云 Adapter，
因为 Adapter 只应该翻译 Provider 协议。
如果将来接入另一种日志后端，
ACL、模板和预算仍应保持一致。

这个设计的代价是前期配置更严格。
新增服务要先注册 Catalog、模板和 Schema，
不能临时拼一条查询去试。
但对真实日志 Agent 来说，
这种摩擦换来的是明确的数据边界。

测试已经覆盖未授权、超窗、水位未过、Schema 错误、
审计失败、Provider 迟到和并发限制。
真实 SLS 联合调查也走的是同一 Gateway，
不是绕过治理直接调用 CLI。

### 追问一：为什么用户不能直接传 Logstore？

Logstore 是物理资源能力。
如果直接接受它，用户就可以试探不属于自己的日志库。
逻辑服务由 Catalog 解析成物理资源，
管理员可以统一维护映射和 ACL。

### 追问二：为什么审计失败要阻止查询？

因为查询发生后无法撤回。
如果先查再补审计，审计系统故障时就会产生无记录访问。
对敏感数据读取，我选择先证明能留痕，再允许调用。

### 追问三：水位线会不会让结果不够实时？

会，这是有意的取舍。
水位线牺牲最新几分钟的实时性，
换取窗口数据更完整。
如果业务需要更实时，可以展示“初步结果”，
但不能把它标成确定性结论。

### 追问四：云端 RAM 和应用 ACL 有什么区别？

RAM 是底层账号能访问哪些云资源，
应用 ACL 是某个业务用户能通过 Agent 查哪些逻辑资源。
两层都需要，应用代码不能替代最小权限 RAM，
RAM 也无法表达所有业务租户规则。

### 边界防守

我可以说默认拒绝和调用前治理已经由代码与测试保证。
我不能说应用网关已经替代云管理员完成全部 RAM 治理，
也不能把单次真实查询说成长期生产权限审计结论。

## 3. 设计租约与Checkpoint，支持任务故障恢复

### 20～30 秒开场

日志调查包含有成本的外部调用，
所以我用任务租约、Attempt Fence 和 QueryStep Checkpoint 做故障恢复。
已完成的当前或基线窗口可以在治理指纹一致时跨重启复用，
旧 Worker 失去租约后不能写回。
如果外部请求结果无法确认，
系统进入人工复核而不是盲目重试。

### 2～3 分钟完整口述

这条的核心问题是：
数据库事务不能包住远端 SLS 请求。

假设当前窗口已经查询成功，
进程在查询基线之前崩溃。
重启后全部重做会重复消耗；
但如果第一个请求已经发出，只是本地超时，
自动重试可能再次执行同一外部调用。

所以我没有声称实现分布式 Exactly Once，
而是把不确定性拆成几个可以持久化的状态。

第一层是 Job Lease。
Worker 从 SQLite 原子领取一份带过期时间的任务，
执行期间持续续租。
如果进程崩溃，租约到期后其他 Worker 可以接管。

第二层是 Attempt Fence。
每次接管都会产生新的尝试编号。
旧进程即使恢复并迟到写回，
数据库也会因为租约持有者或 Attempt 不匹配而拒绝。

第三层是 QueryStep Checkpoint。
当前窗口和基线窗口分别记录 STARTED、SUCCEEDED、FAILED 或 UNKNOWN。
成功结果保存的是归一化聚合证据，
而不是原始日志。

复用时不能只看服务和时间。
我把 Catalog 物理映射、ACL 策略、查询模板、Schema 和预算
组合成治理指纹，并与逻辑输入一起计算哈希。
只要治理身份变化，旧结果就不能复用。

最关键的是 UNKNOWN 状态。
如果调用前明确失败，系统可以记录稳定失败；
如果成功结果已经持久化，系统可以复用；
如果请求可能到达 Provider 但没有收到确定答案，
系统不会把它当成普通失败重试，
而是将调查标为需要人工复核。

这会增加一点人工处理成本，
但避免为了追求自动化而重复产生费用。

我还区分了进程关闭和 Provider 未知。
如果是整个 Worker 收到关闭信号，
它会留下租约等待接管，
不会在取消的 Context 上仓促写一个可能不可靠的终态。

测试覆盖了租约续期、过期接管、旧持有者写入拒绝、
成功步骤跨数据库重启复用、治理漂移拒绝、
Provider 未知和取消传播。

当前 Store 使用 SQLite，
适合本地单实例技术预览。
生产多实例还需要迁移到高可用数据库，
但 Lease、Fence 和 QueryStep 的领域语义可以继续复用。

### 追问一：为什么 Checkpoint 不放在 Eino 里？

Checkpoint 是费用与恢复合同，
不能依赖某个编排框架的内存状态。
放在 Eino 外部后，
框架升级或替换时仍保留相同的复用和失败关闭语义。

### 追问二：这是不是 Exactly Once？

不是严格的外部 Exactly Once。
本地可以防止重复完成和复用已知成功结果，
但无法证明远端在网络不确定时只执行了一次。
所以系统显式保留 UNKNOWN 和人工复核。

### 追问三：为什么治理指纹也要参与复用？

因为相同时间窗口不代表相同访问语义。
管理员可能修改 Logstore 映射、索引、模板或预算。
如果忽略这些变化，旧证据会在新规则下被错误复用。

### 追问四：SQLite 能支持多个 Worker 吗？

代码用租约和 Fence 表达了并发语义，测试也覆盖多连接竞争。
但 SQLite 在吞吐、高可用和跨主机部署上有限，
所以我把当前形态定义为单实例技术预览，
而不是生产级分布式调度器。

### 边界防守

我可以说故障恢复、重复调用保护和未知状态已经实现并测试。
我不会说实现了严格 Exactly Once，
也不会说 SQLite 版本已经经过生产多机压力验证。

## 4. 建立Evidence约束，拦截LLM无依据摘要

### 20～30 秒开场

我把 LLM 放在事实层之后，
先由规则生成 Evidence、Finding 和 Recommendation，
再把最小化、脱敏的聚合证据交给火山方舟。
模型输出必须引用已有 Evidence ID，
建议也只能来自批准列表。
如果它编造、超时或额度不足，系统丢弃草稿并回退，
不会影响主调查成功。

### 2～3 分钟完整口述

这条要解决的是 LLM 很会表达，
但不应该成为日志事实来源。

最直接的方案是把原始日志发给模型，
让它总结发生了什么。
但这会带来四类风险：
原始日志可能含敏感字段，
日志文本可能带提示注入，
Token 成本会随着样本量扩大，
模型还可能从几条样本猜出并不存在的总体规律。

所以我的设计是 Evidence 先于 LLM。
SLS 只返回受限聚合结果，
规则层先比较当前和基线，
生成带 Evidence ID 的 Findings 和确定性 Recommendations。

摘要服务再构造一个最小输入。
里面只有逻辑范围、时间、聚合计数、完整性、
已有结论、已有假设和允许的建议代码。
它不包含原始日志、查询表达式、用户身份、
凭据、Project 或 Logstore。

真实方舟调用也有边界。
请求关闭服务端存储，
限制最大输出 Token，
并要求严格结构化响应。

但结构化响应还不够。
模型回来后，应用层会再次检查：
现象引用的 Evidence ID 是否存在，
建议代码是否真的在规则报告中，
它是否选择了未提供的根因，
输出是否包含受限敏感内容，
Token 用量是否超过预留边界。

任何一项不满足，
模型草稿都不会进入最终报告。
系统使用确定性回退摘要，
调查本身仍然可以成功。

我还做了租户维度的摘要额度。
调用前先预留请求数和 Token，
调用后按 Provider 返回的真实用量结算。
如果 Provider 返回用量未知或结算失败，
系统保守保留额度并拒绝不可信输出。

我没有只在 Prompt 里写“不要编造”，
因为那是软约束。
真正的安全边界来自输入裁剪、严格输出、应用校验和失败回退。

自动化测试覆盖 grounded 草稿、虚构 Evidence、危险建议、
敏感输入、count-only 越界推断、配额拒绝和 Provider 故障。

真实方舟已经在同一次真实 SLS 调查中成功生成摘要。
那次记录了 Token 和延迟，
但我只把它当成联合验收样本，
不会包装成稳定 SLA 或准确率。

### 追问一：Prompt 已经要求不编造，为什么还要校验？

Prompt 是对概率模型的请求，不是强制合同。
输出校验把 Evidence ID、建议代码和根因范围变成确定规则。
模型不遵守时，应用可以确定地拒绝。

### 追问二：为什么不用 RAG 把更多原始日志给模型？

当前任务首先判断错误是否突增，
聚合统计比随机日志样本更适合形成总体证据。
未来可以引入经过脱敏和限量的样本检索，
但仍要让样本属于某个 Evidence，不能绕过治理。

### 追问三：模型失败为什么不让调查失败？

模型负责表达增强，不负责产生事实。
规则报告已经能给出基础结论，
所以模型超时、限额或不合规时应该优雅降级，
而不是把已完成的真实日志调查一起判失败。

### 追问四：如何防止模型在 count-only 上猜根因？

count-only 输入不提供错误类型、实例或根因候选，
输出校验也不允许引用不存在的假设。
测试会故意返回一个看似合理但无证据的根因，
确认系统将它拒绝。

### 边界防守

我可以说真实方舟已接入，Evidence 约束和回退已实现。
我不能说模型已经准确识别真实根因，
也不能把一次 907 Token、1771 毫秒的样本当成长期性能。

## 5. 通过CLI+STS接入真实SLS，避免持久凭据

### 20～30 秒开场

真实 SLS 接入时，
我没有让 Agent 保存长期 AK/SK，
而是复用企业已有的 SSO、STS 和阿里云 CLI Profile。
Go Adapter 只执行固定 SLS 子命令，
限制路径、参数、环境、超时和输出，
CLI 负责读取临时凭据并签名。
这样更贴合实际授权流程，也缩小了凭据暴露面。

### 2～3 分钟完整口述

这条体现的是我根据真实环境调整了技术方案。

最初项目考虑直接使用阿里云 SDK。
SDK 有类型安全和进程内性能优势，
但实际公司环境里，
用户通过 SSO 获取 STS 临时凭据，
再配置到本机阿里云 CLI Profile。

如果为了 Agent 再搭一套 AK/SK 注入和轮换，
不仅工程量大，
还会让 Agent 进程长期接触更多秘密。

所以我把真实 Provider Adapter 改成调用阿里云 CLI。
CLI 从指定 StsToken Profile 读取临时凭据，
负责签名和网络请求；
Agent 不读取 Profile 文件，
配置中也不保存 Token。

不过，CLI 不是天然安全。
如果直接用 Shell 拼接用户输入，
命令注入风险会非常高。

因此我的 Adapter 不执行任意命令字符串。
可执行文件先解析为绝对路径，
Profile、Region、Endpoint、Project 和 Logstore 都经过安全字符校验。
子命令与参数由固定模板构造，
不是用户文本。

运行环境还会清理可能覆盖凭据的变量，
避免外部进程偷偷切换认证来源。
每次调用有超时和最大输出限制，
错误返回也会过滤查询内容和 Provider Body。

查询本身同样不是自由 SQL。
Adapter 只会把 Gateway 批准的资源编译成固定聚合模板。
count-only 模板只执行前后计数，
维度模板才会执行错误类型和实例聚合。

为了避免查询过程中数据变化造成伪精确，
维度分析会在前后再次计数。
如果边界变化，结果会降级为不完整，
不能成为确定性 Evidence。

真实连接的验证分两层。
首先，人工 CLI 检查证明八个 Logstore 的 STS、权限和网络可用。
随后，Agent 在一个主 Logstore 上通过 Query Gateway、
Checkpoint 和 CLI Adapter 完成 count-only 调查，
并继续调用真实方舟生成摘要。

这里我会很明确：
八库“连接可用”不等于 Agent 已实现八库联合分析。
当前 Agent 真实试点仍是单 Logstore。

选择 CLI 的代价是依赖本机安装和插件版本，
进程启动也比 SDK 有额外开销。
但在第一阶段，
复用成熟 STS 认证路径比重新托管长期凭据更重要。

### 追问一：CLI 为什么比 SDK 更适合这里？

不是因为 CLI 普遍优于 SDK，
而是当前组织已经用 CLI Profile 承接 SSO 和 STS。
它减少了新增凭据分发链路。
如果未来有统一的工作负载身份服务，
SDK 也可能重新成为更合适的实现。

### 追问二：怎么避免命令注入？

不通过 Shell 解释整段字符串，
可执行程序和参数分开传递；
命令集合固定，资源字段做白名单校验，
用户也不能直接提供查询表达式或物理资源。

### 追问三：STS 过期会怎样？

CLI 会返回认证失败，
Adapter 将它转换成稳定、脱敏的 Provider 错误。
当前由用户重新从 SSO 获取并更新 Profile，
系统不会自动切换账号或保存旧 Token。

### 追问四：为什么只做单 Logstore？

真实 DAM 的八个日志库字段能力不完全一致。
第一阶段先用主库的 env 和 level 跑通 count-only，
可以用最小范围验证整个真实 Agent 链。
多库统一 Evidence 需要单独设计资源组、配额和合并语义，
不应该假装已经完成。

### 边界防守

我可以说真实 SLS 已经通过 CLI + STS 接通，
并完成单库 Agent 联合调查。
我不能说 Agent 已自动覆盖全部八库，
也不能说 CLI 方案已经通过生产吞吐验证。

## 6. 实现可靠投递与死信重放，隔离调查失败

### 20～30 秒开场

我把调查执行和结果投递拆成两条可靠链。
报告先持久化，DeliveryWorker 再负责飞书 Reply/Patch，
并使用独立租约、超时、失败分类、指数退避和死信。
因此消息平台暂时失败时，
系统只重试投递，
不会重新查询 SLS 或再次调用 LLM。

### 2～3 分钟完整口述

这条解决的是一个常被忽略的问题：
调查成功和用户收到消息不是同一件事。

假设日志已经查完，报告也已经生成，
但飞书 API 短暂不可用。
如果把发送卡片放在调查事务里，
整个任务会被标成失败。
上游一重试，
系统可能再次查询 SLS、再次消耗 LLM，
最后用户还可能收到重复卡片。

所以我把投递建模成独立的持久化任务。
调查 Worker 成功时，
原子保存报告和待投递记录。
报告从这一刻起就是事实，
不依赖飞书是否在线。

DeliveryWorker 再从数据库领取消息租约。
它为每次发送设置独立超时，
并把错误分类为临时、永久、取消或未知。

临时错误按指数退避重试，
但退避有上限；
永久错误或达到最大次数后进入 Dead Letter，
不会无限占用队列。

飞书卡片还有顺序语义。
初始 Reply 会创建远端卡片 ID，
后续进度和终态通过 Patch 更新同一张卡。
数据库会保存卡片绑定和投递序号，
避免旧进度覆盖已经成功的终态。

死信也不能随便重放。
例如一条过时的进度消息，
如果终态已经发出，就不应该再覆盖卡片。
Operator 重放前会检查投递类型和当前投影，
只允许安全的消息重新入队。

我没有在 HTTP 或飞书事件回调里同步完成整条调查，
因为调查时延和平台请求时限不匹配。
入口只负责幂等接单，
Worker 与 Delivery 在后台分别推进。

飞书功能方面，
接收消息事件、解析卡片动作、Reply/Patch Sender、
卡片渲染和可靠投递代码都已经实现。
完整合同有自动化和全链测试。

由于当前没有真实企业应用权限，
我用本地 Web Sender 复用同一 Delivery 合同完成联合验收。
所以准确说法是“飞书功能已实现，真实平台验收待权限”，
既不弱化已经完成的功能，也不把待验收平台说成已经上线。

这套设计的代价是最终一致性。
调查已经成功时，用户可能晚几秒看到终态；
系统也要额外维护死信和重放工具。
但它把真实调查费用与消息平台波动隔离开了。

### 追问一：为什么不能直接同步发送？

同步发送会把入口、调查和飞书三段时延绑在一起。
任何一段超时都可能让上游重试，
造成重复调查或重复消息。
持久化投递让报告和消息分别恢复。

### 追问二：所有发送失败都重试吗？

不会。
临时网络或限流错误可以退避重试，
参数错误、权限错误等永久失败进入死信。
取消和未知状态还要按当前上下文单独处理。

### 追问三：如何避免旧进度覆盖终态？

每种投递有顺序和当前卡片投影。
领取、完成和死信重放都会检查最新状态。
如果终态已经推进，过时进度即使进入死信也不能重新覆盖。

### 追问四：飞书到底完成到什么程度？

接收事件、动作映射、卡片渲染、Reply/Patch 和可靠投递代码已完成，
对应合同有自动化测试。
真实应用权限下的 WebSocket、OpenID 和卡片交互还待平台验收。

### 边界防守

我可以说飞书功能实现完成，可靠投递与死信行为有测试。
我不能说真实企业飞书已经联调上线。
本地 Web 联合 E2E 证明应用主链，
不替代真实平台协议验收。

## 7. 搭建Golden与Replay评测，防止Agent退化

### 20～30 秒开场

我为 Agent 建立了 Golden Dataset、版本指纹、结果快照和 Replay Compare。
评测不只看是否返回结果，
还检查 Evidence 引用、误导结论、危险建议和反证场景。
版本比较直接读取相同快照，
如果数据合同不兼容就明确拒绝比较，
避免用变化中的真实日志得出伪精确结论。

### 2～3 分钟完整口述

这条解决的是 Agent 迭代以后“怎么知道它真的变好了”。

传统后端函数往往有明确输入输出。
Agent 报告同时包含规则、证据和自然语言，
修改一个阈值或 Prompt，
表面上可能更流畅，
实际却可能引用不存在的证据或给出过度结论。

只挑几个成功案例人工看，
很容易产生确认偏差。
直接在真实 SLS 上重跑两个版本也不公平，
因为日志数据和索引状态一直在变化。

所以我建立了三层离线评测。

第一层是 Golden Dataset。
每个案例都有固定请求、受控 Provider 结果和预期门禁。
案例既包括错误突增，
也包括零基线、不完整证据和看似合理但具有误导性的结论。

第二层是评测快照。
每次运行保存唯一 Run ID、数据集版本、规则版本、
稳定版本指纹、输入摘要、输出和父子 lineage。
这样过一段时间仍能知道某个结果是由什么合同产生的。

第三层是 Replay Compare。
比较两个版本时不重新访问 SLS 或 LLM，
而是加载严格快照。
只有数据集和合同兼容时才输出差异；
如果不可比，就返回 incomparable，
而不是强行算一个没有意义的提升百分比。

评测门禁不只检查“成功率”。
它还检查每条 Finding 是否引用真实 Evidence，
不完整数据是否被错误当成结论，
Recommendation 是否越过只读边界，
摘要是否编造 Evidence 或敏感内容。

我还准备了专家反馈账本和灰度演练结构。
当前反馈主要是合成和离线种子，
未来获得真实排障复盘后，
可以脱敏加入回归集，
再决定某个版本是否值得进入更大范围验证。

我没有直接做线上 A/B。
因为当前还没有稳定真实流量、专家标签和自动回滚平台，
线上实验成本与风险都太高。
先用 Golden 和 Replay 锁住安全底线更现实。

自动化测试已经覆盖固定 Golden 全通过、
误导性 Finding 失败关闭、
唯一 Run ID、稳定版本指纹、
快照持久化、回放 lineage 和不可比较边界。

这些结果说明已定义场景可以防回归，
不能推出真实故障根因准确率。
我不会在简历上写一个没有专家标注支撑的百分比。

### 追问一：为什么单元测试不够？

单元测试能证明局部函数，
但最终报告跨越查询、规则、Evidence 和摘要。
Golden 场景验证的是端到端语义门禁，
特别是“什么时候不应该下结论”。

### 追问二：为什么 Replay 不重新调用真实系统？

重新调用会遇到变化中的日志和模型随机性，
两个版本不再处于同一输入。
读取同一快照才能把差异主要归因于规则或版本变化，
也能避免重复云成本。

### 追问三：什么情况下两个版本不可比较？

数据集版本、输入合同或关键评测语义不兼容时，
系统就不输出 Delta。
宁可明确说不可比较，
也不生成看起来精确但没有共同基线的数字。

### 追问四：怎样把真实反馈加入评测？

先从排障复盘中提取脱敏 Evidence 和专家结论，
记录模板、环境、失败类型和反馈版本。
经过审核后加入回归集，
不直接保存原始敏感日志。

### 边界防守

我可以说离线 Golden、快照和回放门禁已经实现并测试。
我不能说它已经证明线上准确率，
也不能把合成反馈描述成生产专家数据。

## 8. 最后怎样选择脚本

如果简历使用候选一、二、四，
面试叙事顺序是：
我怎样限制 Agent 路径，
怎样限制真实工具，
怎样限制模型输出。

如果简历使用候选三、六，
叙事顺序是：
调查中断怎样恢复，
报告成功但投递失败怎样恢复。

如果简历使用候选五、七，
叙事顺序是：
我怎样接入真实系统，
又怎样防止后续版本退化。

无论选择哪条，
都先给结论，再讲问题、方案、效果和取舍。
面试官追问到未完成部分时，
直接说明当前边界和下一步，
不要用“基本完成”“差不多上线”这类模糊表达。

> 💡 **一句话记住**：每条简历都要讲成一个闭环故事——真实问题逼出设计选择，代码与测试证明效果，边界和代价体现工程判断。
